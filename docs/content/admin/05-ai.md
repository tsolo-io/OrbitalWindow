# AI models

OrbitalWindow keeps a library of AI models (large language models from Hugging Face) on the server.
People with the **AI manager** role download and delete models on the **AI** page. Admins can do
this too.

## AI engine: vLLM or llama.cpp

**Settings → AI → AI engine** chooses the program that runs the AI session (`OW_AI_ENGINE` in
`.env` sets the first value):

| | vLLM | llama.cpp |
|---|---|---|
| Model format | safetensors (for example `Qwen/Qwen3-8B`) | GGUF (for example `Qwen/Qwen3-8B-GGUF`) |
| GPUs | NVIDIA. Intel only in theory, see below | NVIDIA, Intel and AMD |
| Strong points | Fast for many people at once | Compressed models (4–8 bits), so larger models fit; small images |

**vLLM does not work on Intel GPUs.** On an Arc A770, a chat longer than about 5,000 tokens hangs
the GPU, and Open WebUI's built-in tools make every chat that long (ADR 0038). Use llama.cpp on
Intel hosts. On AMD hosts, llama.cpp is the only engine.

The engine applies when the session is next started. The session list shows only the models that
the engine can run: download a GGUF version of a model for llama.cpp. llama.cpp's image follows
the GPU setting (`ghcr.io/ggml-org/llama.cpp:server-<cuda|intel|rocm>-<build>`, build
`OW_LLAMACPP_BUILD`); the Intel one is about 16 GB.

## Who manages models

On **Users**, open a user's **Actions** and choose **Make AI manager**. The **AI** link then
appears in their header (after their next page load). Removing the role takes effect on their next
click. A user without GPU access cannot be an AI manager: give them GPU access first.

## Downloading a model

1. Find the model on [huggingface.co](https://huggingface.co/models) and copy its id, for example
   `Qwen/Qwen3-8B`.
2. On **AI**, enter the id and press **Inspect**. It shows:
   - the download size, the number of parameters and the licence;
   - whether the model is *gated*;
   - for a GGUF repository, a choice of **Weights to download**: one file per quantisation
     (`Q4_K_M`, `Q8_0`, …). `Q4_K_M` is chosen first: a good balance of size and quality.
3. Press **Download**. The download runs in the background, one at a time, and continues if you
   close the page or OrbitalWindow restarts.
   - **Cancel** stops it; **Resume** continues where it stopped.

Only the files needed to run the model are downloaded: for vLLM the weights in safetensors format,
the configuration and the tokenizer; for llama.cpp the one chosen GGUF file (with its parts, if it
is split). A model folder holds one GGUF file: to try another quantisation, delete the model first.

Models are stored in `OW_ROOT/shared/models/<organisation>/<model>`. The page shows the free space
on that disk and how much the models use. A typical 8B model is about 16 GB, and a 32B model about
65 GB.

## Will it fit on the GPU?

**Inspect** and the **GPU fit** column estimate the GPU memory a model needs when it runs:
- its weights;
- a cache for 32,768 tokens of conversation (the *context*), the least that coding tools such as
  OpenCode need;
- some overhead.

The estimate is compared with the server's largest GPU:

| Shown | Meaning |
|---|---|
| fits | Fits in the share of the GPU that the AI engine uses: 90 % for vLLM, 95 % for llama.cpp. |
| fits (GPU busy) | Fits, but desktops or other programs are using the GPU right now. |
| tight | Needs nearly the whole GPU. A shorter context may make it fit. |
| too big | Needs more memory than the GPU has. Pick a smaller model. |

**Suggestions from llmfit** lists models that suit the GPU, from the llmfit project's catalogue
(only well-known publishers). Press **Inspect** next to one for its real size and fit.

The llmfit version is set with `OW_LLMFIT_IMAGE` in `.env`. Newer tags are listed at
https://github.com/AlexsJones/llmfit/pkgs/container/llmfit; change the tag and run `make start`.

## Running a model (the AI session)

At the top of the **AI** page, choose a downloaded model, the GPU, the context length (how much
text the model sees at once) and, with vLLM, how much of the GPU's memory it may use. These are
filled in from the estimate: the context is the longest that fits, up to 65,536 tokens and the
model's own maximum. Press **Start**. llama.cpp takes only the memory the model and its context
need, and serves 4 requests at once from one shared cache.

- **Context:** a longer context lets the model handle longer conversations and the large requests
  of coding tools. It needs more GPU memory for its cache, so on a given GPU it pushes you towards
  smaller models. Below 32,768 tokens the page warns that coding tools won't work. The dashboard
  shows every user the running model's context.

- **Loading** takes a few minutes the first time; the page shows vLLM's log meanwhile. The
  dashboard tells every user when the model is ready.
- **One model** runs at a time. It keeps running until someone presses **Stop the session**, which
  frees the GPU memory at once.
- If it fails (for example, not enough GPU memory because desktops use it), the page shows the end
  of the log. Stop GPU-heavy work or choose a smaller share or context, then start again.

The first start needs the engine's image: for vLLM `OW_VLLM_IMAGE` (CUDA, about 30 GB) or
`OW_VLLM_INTEL_IMAGE` (Intel XPU, about 17 GB); for llama.cpp the image for the GPU (see above).

On an **Intel Arc A-series or Flex** GPU the session runs in float16 with Triton attention, and its
context cache is limited to 3.75 GB: these GPUs can't use larger memory blocks. The page suggests
a context that fits this limit and refuses a longer one. See
[Preparing an Intel host](01-install-intel.md).

### Using the model from code

The session serves the OpenAI API. Under **Use the model from code** you find the address, the API
key and a Python example. By default only services on the server reach it (Open WebUI,
OrbitalWindow). Switch on **Reachable from other computers** to use it from desktops, laptops or
other servers at `https://<host>/v1`; every call needs the key. **New key** replaces the key.
Both changes apply at the next start.

This session key is meant for administrators and other servers. Users don't need it: they use the
LLM gateway (below).

### The API for users (LLM gateway)

Programs and editors use the model through the **LLM gateway** (LiteLLM, ADR 0045) at
`https://<host>:8443/v1`. It runs all the time, also without a model, and OrbitalWindow manages it:

- **Keys:** on the dashboard, **AI model → Use the model from your own code**, each user creates
  their own key (`sk-ow-…`) and can replace it. A disabled user's key is blocked, and a deleted
  user's key is deleted. Key changes are in the audit log (`api.key.create`, `api.key.renew`).
- **The model:** when a session runs, the gateway gets its model; when it stops, the model is
  removed. Programs keep the same address and key when another model runs.
- **Endpoints:** chat (`/v1/chat/completions`), code completion (`/v1/completions`), embeddings
  and the model list. Nothing else of LiteLLM is reachable from outside; it has no internet.
- **No limits** per user for now; they can be set when one user's requests slow down the others.
- Its data (keys, use per key) is in the database `litellm` on the database server, so it is in the
  system backups.

LiteLLM's own admin pages (usage per key and model, request logs, keys, models) are off. To look at
them, set `OW_LLM_ADMIN_UI=true` in `deploy/.env` and run `make update`. They are never reachable
through Traefik, so use an SSH tunnel from your PC:

1. On the server, find the gateway's address:
   `docker inspect ow-llm-gateway --format '{{(index .NetworkSettings.Networks "ow-ai").IPAddress}}'`.
2. On your PC: `ssh -L 4000:<that address>:4000 <you>@<server>`.
3. Open `http://localhost:4000/ui` and log in as `admin` with the master key
   (`docker exec ow-llm-gateway printenv LITELLM_MASTER_KEY` on the server).

Changes there to OrbitalWindow's keys (`ow-…`) and models (`ow-session-…`) are undone within a
minute; other changes stay. Set `OW_LLM_ADMIN_UI=false` again when you are done.

The session key does not work at `:8443/v1`, and a user's key does not work at `https://<host>/v1`.
The chat's own keys (`sk-…` at `:8443/api`, made in the chat's settings) still work for now.

### Code completion (fill-in-the-middle)

Editors such as Zed and Continue (VS Code) complete code while users type. That needs a model with
*fill-in-the-middle* (FIM) tokens, and a model made for code gives good suggestions. The
**Downloaded models** table shows it in **Code completion**:

- **Coder**: FIM tokens and a coder model (for example `Qwen/Qwen2.5-Coder-3B`): good suggestions.
- **Possible**: FIM tokens, but a general model: it works, the suggestions may be poor.
- **No**: no FIM tokens: editors can't complete code with it; chat still works.

OrbitalWindow reads this from the model's files. If it is wrong, set it by hand with the menu next
to it (**Automatic** goes back to what the files say). The dashboard tells users what the running
model can do.

## The chat (Open WebUI)

While the session runs, everyone gets **Open chat** on the dashboard. It opens Open WebUI at
`https://<host>:8443/`, already signed in with their OrbitalWindow account. Each person's chats are
private to them and kept when the session stops.

- **OrbitalWindow admins** are Open WebUI admins (its admin panel: settings, all users); everyone
  else is a normal user. This follows OrbitalWindow at every sign-in.
- **API keys:** users create their own in the chat (*Settings → Account → API keys*) and call the
  model from Python or MATLAB at `https://<host>:8443/api` (see the user help page *AI chat and
  models*). This works from any computer that can reach the server, without a desktop.
- **Tools:** the chat lets the model use built-in tools (the time, search in past chats, notes).
  With vLLM this needs a model family that vLLM can call tools for (Qwen, Llama 3, Mistral,
  gpt-oss, Granite, OLMo 3, Gemma 4); with llama.cpp the model's own chat template handles tools.
  OrbitalWindow turns it on by itself. Other models still chat, with tools
  described in the prompt, which works less well.
- **Thinking models** (Qwen3, Qwen3.5): the chat folds the model's reasoning into a collapsible
  *Thought* block above the answer.
- **Port 8443** must be reachable from the users' PCs. With the self-signed certificate, browsers ask
  once to accept it for this port too.
- **Data:** chats, keys and settings are in `OW_ROOT/state/openwebui`, which the state backup
  includes.

The Open WebUI version is set with `OW_OPENWEBUI_IMAGE` in `.env`.

## Benchmarks

**Benchmark** next to a downloaded model runs a coding benchmark: **HumanEval+** (164 tasks, a few
minutes) or **MBPP+** (378 tasks). If the model isn't running, it is started first; if another
model runs, you are asked before it is replaced. The page shows the step and how many tasks are
done, and **Cancel** stops it.

The model writes a Python function for each task, and the functions are run against tests in a
sealed container (no network). The *plus* score is the share of tasks that pass all tests. The
latest score shows next to the model; **Benchmarks** in the header lists every run for everyone,
with a full report per run. Results are kept in `OW_ROOT/state/benchmarks`.

## Gated models (Llama, Gemma, …)

1. Log in to Hugging Face, open the model's page and accept its licence.
2. Create a **read** token under *Settings → Access Tokens*.
3. Store the token on the **AI** page under **Hugging Face token**.

The token is kept in `OW_ROOT/state/hf_token` (readable only by the service) and is used only for
downloads. It isn't included in the audit log.
